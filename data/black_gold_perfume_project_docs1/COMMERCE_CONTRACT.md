# COMMERCE CONTRACT - عقد التجارة المقترح

هذا عقد تصميم قبل كتابة الكود، وليس وصف API منفذ. يثبت التنفيذ النهائي بصيغة OpenAPI في Phase 2 بعد حسم D02/D04/D05/D06/D07/D08. أي تعديل لقواعد المال أو الحجز يحدث الاختبارات والواجهة معًا.

## 1. الملكية وحدود الثقة

- Laravel هو صاحب السعر والمخزون والخصومات والشحن والضريبة وصحة انتقال حالات الطلب.
- المتصفح يرسل معرف النسخة والكمية والعنوان وطريقة الشحن/الدفع؛ لا يقرر الإجمالي أو حالة الدفع.
- الكتالوج العام قابل للتخزين المؤقت بقواعد واضحة؛ السلة وquote والطلب وبيانات الإدارة خاصة ولا تخزن في cache مشترك.
- تحدد Phase 2 مسار الجلسة: اتصال المتصفح بـLaravel أو عبر Next.js. لا تخلط نموذجين دون داعٍ، ولا تلغ تفويض Laravel عند استخدام وسيط.
- جلسة الضيف أو رابط وصول محدود الصلاحية يثبتان ملكية السلة/الطلب؛ رقم الطلب ومعرفه العام ليسا تصريح وصول.
- لو اعتمدت جلسات cookies، توثق خصائص Secure/HttpOnly/SameSite وحماية CSRF وCORS للنطاق الفعلي. لا تخزن أسرار المزود أو رموز الإدارة في الواجهة.

## 2. نموذج البيانات الأدنى

| الكيان | مسؤولياته |
| --- | --- |
| Product | الاسم والوصف والتصنيف وslug وحالة النشر؛ لا يكفي وحده لشراء نسخة |
| ProductVariant | SKU فريد وحجم وتركيز وسعر وعملة وحالة البيع |
| ProductMedia | الأصل والنسخة/المنتج وترتيب العرض وalt واعتماد المطابقة |
| Inventory / InventoryMovement | الكمية الفعلية والحجز وحركات دخول/شحن/إرجاع/تصحيح مع السبب والمنفذ |
| Cart / CartItem | ملكية السلة ومعرف النسخة والكمية؛ لا يحجز المخزون افتراضيًا |
| Quote | نسخة إجمالي من الخادم وشروط الشحن وصلاحية العرض؛ لا يعد وعدًا بحجز |
| Order / OrderItem | بيانات العميل والتوصيل ولقطة الاسم وSKU والسعر والكمية والعملة وقت الإنشاء |
| StockReservation | الكمية والطلب والحالة والانتهاء للحجز غير المؤكد |
| PaymentAttempt / PaymentEvent | محاولة دفع، معرف المزود الفريد، حالتها، وسجل الأحداث التي تمت معالجتها |
| Shipment / OrderStatusHistory | مرجع التسليم وتتبع الحالة والتغييرات الإدارية |
| IdempotencyRecord | نطاق صاحب الطلب والمفتاح وبصمة المدخلات وربط النتيجة بالطلب |
| BundleComponent | يضاف فقط إذا اعتمد D07؛ مكونات وكميات وسياسة العينات للباقة |

الدخول الإداري والأدوار منفصلان عن قرار إنشاء حسابات للعملاء. جداول التصنيفات والإعدادات تضاف بقدر الحاجة الفعلية.

## 3. قواعد المال والتسعير

- تخزن القيم كأعداد صحيحة بأصغر وحدة للعملة المعتمدة، مع رمز العملة ودقة التحويل الخاصة بها؛ لا تستخدم float لحساب الإجماليات.
- ثبّت في D02: هل الأسعار تشمل الضريبة؟ أين التقريب؟ وما قواعد الشحن والخصم؟ لا تضف نسبة أو إعفاء مخترعًا.
- يعرض quote: العناصر، subtotal، الخصم إن اعتمد، الشحن، الضريبة بحسب السياسة، وgrand_total. لا تعد إضافة الضريبة مرتين إذا كانت شاملة.
- يحتفظ الطلب بلقطة بيانات السعر والمنتج والتوصيل. تغيير الكتالوج بعده لا يغير الطلب القديم.
- عند تغير السعر أو الشحن أو انتهاء quote، يرجع الخادم تعارضًا مفهوما وإجماليًا جديدًا؛ لا يخصم مبلغًا جديدًا قبل مراجعة العميل.
- مزود الدفع يتلقى المبلغ والعملة من الطلب. أي إشعار لا يطابق معرف الطلب/المحاولة والمبلغ والعملة يدخل استثناء للمراجعة.

## 4. المخزون والحجز

نموذج مقترح يثبت في D06:

- on_hand: مخزون فعلي لم يغادر المستودع. reserved: وحدات محجوزة لطلبات غير مشحونة. available = on_hand - reserved.
- القيد الدائم: 0 ≤ reserved ≤ on_hand. المخزون المجهول لا يعرض كمتاح.
- عند إنشاء طلب: قفل صفوف المخزون بترتيب ثابت، إعادة فحص الكميات، حجزها وإنشاء الطلب داخل معاملة واحدة. فشل عنصر يلغي العملية كلها.
- انتقالات انتهاء الحجز والتأكيد والإلغاء والشحن تقفل الطلب والحجز والمخزون بترتيب متسق وتتحقق من الحالة الحالية داخل المعاملة؛ لا يسمح لنجاح الدفع وانتهاء الحجز بتحرير وتأكيد نفس الوحدات معًا.
- لا تجر مكالمة بوابة دفع أو شحن أثناء إبقاء أقفال قاعدة البيانات.
- الحجز غير المؤكد له expires_at وفق D06؛ حجز الطلب المؤكد يتحول إلى تخصيص لا تحرره مهمة انتهاء الحجوزات.
- نجاح الدفع أو تأكيد COD لا يخصم الكمية مرة أخرى؛ تبقى مخصصة حتى الشحن. عند الشحن تنخفض on_hand وreserved مرة واحدة مع سجل حركة.
- إلغاء طلب غير مشحون أو انتهاء حجز غير مؤكد يحرر الحجز مرة واحدة. إعادة حدث الإلغاء لا تضيف مخزونًا.
- المرتجع لا يضاف إلى المخزون القابل للبيع إلا بعد الاستلام والفحص وفق السياسة. refund وحده لا يعيد المخزون تلقائيًا.
- لا يسمح بتصحيح on_hand إلى أقل من reserved دون إجراء معالجة موثق للطلبات المتأثرة.
- الباقة، إن اعتمدت: تحجز كميات كل المكونات ذريًا. المتاح أقل عدد يمكن تجميعه من المكونات المطلوبة؛ لا تستخدم رقم مخزون مستقلًا يتجاهلها.
- اختبار آخر قطعة يستخدم اتصالين/طلبين متزامنين على MySQL، لا اختبارًا متسلسلًا أو SQLite بديلًا لسلوك الأقفال.

تعتمد طريقة التنفيذ على معاملات وقفل مناسب؛ راجع [Laravel: Pessimistic Locking](https://laravel.com/docs/queries#pessimistic-locking).

## 5. الطلب والدفع والتنفيذ حالات مستقلة

| المجال | حالات أولية مقترحة |
| --- | --- |
| الطلب | pending، confirmed، cancelled، expired، exception |
| الدفع | unpaid، pending، paid، failed، refund_pending، refunded |
| التنفيذ | unfulfilled، packing، shipped، delivered، returned |

- pending يبدأ بعد حجز صالح. الدفع الإلكتروني المؤكد أو قبول طلب COD وفق السياسة يؤكد الطلب.
- العودة من صفحة المزود تعرض «جارٍ التحقق» حتى يثبت الخادم النتيجة. COD يبدأ unpaid؛ تأكيد الطلب ليس إثبات تحصيل.
- فشل محاولة دفع لا يعني بالضرورة إلغاء الطلب فورًا؛ إعادة المحاولة مسموحة فقط وفق الحجز والسياسة، ولا تسمح بتحصيلين للطلب.
- لا يرجع حدث failed متأخر دفعًا paid إلى failed. حالة refunded لا تمحى بوصول حدث نجاح قديم.
- عند وصول تحصيل بعد انتهاء/إلغاء الحجز: يسجل المال المدفوع، ويوضع الطلب في exception؛ لا يخفي نجاح التحصيل ولا يؤكد الطلب رغم نفاد الكمية. يعالج بحجز جديد إن سمحت السياسة أو استرداد عبر المزود ومسؤول محدد.
- انتقال حالة حساس يتم بصلاحية ومعاملة وسجل تاريخ. الإلغاء بعد الدفع ينشئ مسار استرداد؛ مجرد تغيير الحالة إلى cancelled لا يعني إعادة المال.
- يثبت جدول انتقالات نهائي واختباراته قبل الربط. الاسترداد الكامل مطلوب إذا اعتمدت مدفوعات مسبقة؛ الاسترداد الجزئي يحتاج قرار نطاق مستقل.

## 6. API مبدئي

كل المسارات أدناه مقترحة تحت /api/v1. يثبت الشكل النهائي قبل بناء العملاء.

| الإجراء | المسار المقترح | الملاحظة |
| --- | --- | --- |
| عرض الكتالوج | GET /products وGET /products/{slug} | pagination وفرز وفلاتر بقائمة مسموحة؛ إخفاء المسودات |
| إدارة السلة | POST /carts ثم GET /cart وPOST/PATCH/DELETE /cart/items | الجلسة تثبت الملكية؛ تغيير عنصر بالنسخة والكمية فقط |
| حساب الإجمالي | POST /checkout/quote | يتحقق من العنوان والشحن ويعيد quote_id وexpires_at |
| إنشاء طلب | POST /orders | quote_id وIdempotency-Key وبيانات معتمدة؛ يعاد التحقق قبل الحجز |
| بدء الدفع | POST /orders/{id}/payment-attempts | ملكية الطلب وحالة تسمح بالدفع؛ معرف محاولة ثابت لإعادة المحاولة |
| حالة الطلب | GET /orders/{id} | تفويض لكل طلب أو رابط آمن وفق D05؛ أقل بيانات لازمة |
| إشعارات المزود | POST /payments/{provider}/webhook | توقيع المزود؛ لا يعتمد على cookie المتصفح |
| الإدارة | /admin/... | دخول وصلاحيات وتدقيق؛ لا تتاح بالمسارات العامة |

شكل نجاح موحد، وأخطاء تحتوي code وmessage وfield_errors عند الحاجة وrequest_id دون تفاصيل داخلية. 422 للتحقق، و409 للتعارض، و401/403 للدخول والصلاحيات، و429 لتحديد المعدل؛ لا تخلط رسالة فشل مزود مع نجاح عملية تجارية.

تثبت أمثلة لأخطاء PRICE_CHANGED وOUT_OF_STOCK وQUOTE_EXPIRED وIDEMPOTENCY_CONFLICT وPAYMENT_PENDING. لا يلزم نقل هذه الأسماء حرفيًا ما دام العقد الفعلي ثابتًا ومختبرًا.

## 7. التكرار والدفع الخارجي

- قيد فريد على نطاق صاحب الطلب + Idempotency-Key، وبصمة للمدخلات. نفس المفتاح ونفس البيانات يعيدان نفس النتيجة؛ نفس المفتاح ببيانات مختلفة تعارض.
- يحجز المفتاح وإنشاء الطلب في مسار ذري؛ لا تنفذ طلبين ثم تحاول إزالة التكرار بعدهما.
- يحتفظ checkout بنفس المفتاح عند double-click أو retry، ويرتبط quote المستهلك بطلب واحد؛ إعادة إرسال quote نفسه بمفتاح جديد لا تنشئ طلبًا ثانيًا.
- يحدد العقد مدة الاحتفاظ بالمفتاح؛ لا تنتهي قبل نافذة إعادة المحاولة المتوقعة. يبقى ربط محاولة المزود بالطلب دائمًا محفوظًا.
- لكل محاولة دفع معرف ثابت. طلب المزود يعاد بمفتاح التكرار نفسه إذا كان يدعم ذلك. عند timeout غير محسوم نستعلم عن النتيجة أو نصالحها قبل إنشاء محاولة جديدة.
- لا يبدأ طلبان متزامنان محاولتي تحصيل نشطتين لنفس الطلب؛ يفرض الخادم محاولة غير محسومة واحدة، ولا يسمح بالمحاولة التالية إلا بعد حسم السابقة وفق حالة المزود.
- إشعارات الدفع: التحقق وفق وثائق المزود، معرف حدث فريد، وتحديث تجاري ذري. لا تعتمد على ترتيب الوصول ولا redirect.
- تعالج الأحداث المتكررة دون تكرار خصم المخزون أو إرسال إشعار أو استرداد. القيد على الحدث لا يغني عن حماية انتقال حالة الطلب.
- تضبط سياسة retries وtimeouts ومصالحة الحالات العالقة. الأحداث المقبولة تحفظ بشكل موثوق قبل الإقرار باستلامها حتى لا تضيع عند تعطل worker.
- ترسل الإشعارات بعد commit، مع سجل إرسال/منع تكرار مناسب. فشل البريد لا يعيد إنشاء الطلب. راجع [Laravel: Jobs and Database Transactions](https://laravel.com/docs/queues#jobs-and-database-transactions).
- تفاصيل التوقيع والتحقق من حالة الدفع تعتمد على المزود الذي يحسمه D04؛ لا تختار بوابة ضمن هذا العقد.

## 8. متطلبات أمان الاختبار

اختبارات ملكية السلة والطلب والإدارة وcache العابر للمستخدمين إلزامية. راجع [Next.js: Data Security](https://nextjs.org/docs/app/guides/data-security) و[Self-Hosting: Caching](https://nextjs.org/docs/app/guides/self-hosting#caching-and-isr) عند تحويل العقد إلى إعدادات فعلية. هذه المراجع لا تستبدل اختبار التفويض في Laravel.
