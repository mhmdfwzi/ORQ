# UNIVERSAL WORK RULES — Mandatory for All AI Agents

هذه القواعد إلزامية لـ Codex وGemini وأي مساعد يغير ملفات المستودع.

## 1. افحص قبل أن تعدّل
- اقرأ README الجذر ودليل الوثائق وPROJECT_BRAIN والملف المرتبط بالمهمة، وحدد المرحلة الحالية والقرارات التي تعتمد عليها.
- افحص بنية المجلد والـ package managers والإصدارات الحالية وملفات البيئة المثالّية. حتى مراجعة 2026-10-28 لا توجد تطبيقات أو Git؛ لا تفترض أوامر تشغيل أو diff غير متاحة.
- لا تفترض أن المشروع يحتوي إعدادًا أو مكتبة لمجرد ذكرها في الوثائق.
- لا تثبّت أو تحدّث حزمًا جماعيًا دون حاجة واضحة.
- لا تستبدل ملفات أو إعدادات موجودة قبل فهم أثر ذلك.

## 2. نطاق المهمة
- نفّذ المهمة المطلوبة فقط.
- لا تعِد كتابة ملفات غير مرتبطة لمجرد تفضيل أسلوبي.
- لا تغيّر تصميمًا معتمدًا أو API contract أو قاعدة بيانات دون توثيق السبب.
- إذا اكتشفت مشكلة خارج النطاق تمنع المهمة، اشرحها واقترح أصغر تعديل لازم.
- لا تحذف كودًا أو بيانات أو migrations دون فهم التبعات.

## 3. العمل الآمن
- لا تضع أسرارًا أو مفاتيح API أو بيانات عملاء في الكود أو Git.
- لا تستخدم بيانات إنتاج حقيقية في الاختبارات.
- لا تنفذ أوامر destructive مثل حذف قاعدة البيانات أو إعادة ضبطها دون موافقة صريحة.
- لا تغيّر `.env` الحقيقي؛ حدّث `.env.example` عند الحاجة مع قيم وهمية فقط.
- استخدم validation على الخادم، وصلاحيات مناسبة، ومعاملات قاعدة البيانات في العمليات الحساسة.
- لا تثق بمدخلات السعر أو الخصم أو الإجمالي من الواجهة.
- تعامل مع webhooks كطلبات غير موثوقة وتحقق من توقيعها وفق مزود الدفع.

## 4. جودة الكود
- اتبع أنماط المشروع الموجودة عندما تكون سليمة.
- لا تضع منطق الأعمال داخل React components أو Controllers ضخمة.
- في Laravel، استخدم Form Requests للتحقق، وسياسات authorization، وطبقة واضحة لمنطق الأعمال عند الحاجة.
- في Next.js، افصل Server Components عن Client Components حسب الحاجة، وتجنب تحويل الصفحة كلها إلى client بلا سبب.
- استخدم أسماء واضحة وأخطاء متسقة.
- لا تضف abstraction أو dependency لمجرد احتمال استخدام مستقبلي.

## 5. قواعد التصميم
- اقرأ `ART_DIRECTION.md` و`DESIGN_SYSTEM.md` قبل تعديل الواجهة.
- لا تستبدل الهوية الفنية بتصميم عام أو قالب افتراضي.
- لا تضع صورًا اصطناعية مكان صور المنتج الحقيقية بطريقة توهم العميل بأنها العبوة الحقيقية.
- لا تجعل الحركة تعطل الشراء أو القراءة.
- اختبر RTL والموبايل، لا تعتمد على معاينة Desktop فقط.
- لا تستخدم ألوانًا أو مسافات عشوائية خارج tokens دون توثيق مبرر.
- لا تضف نصوصًا أو تقييمات أو أعداد مبيعات أو شهادات غير حقيقية.

## 6. الاختبارات والتحقق
بعد كل تغيير ذي معنى، نفذ الفحوص المناسبة لنوعه. تعديل الوثائق يحتاج مراجعة اتساق ومراجع، ولا يستلزم اختبارات تطبيق غير موجود. عند تغيير الكود:
1. شغّل formatter/linter المتاح للمشروع.
2. شغّل الاختبارات ذات الصلة.
3. شغّل type checking أو build للواجهة عندما يكون ذلك ممكنًا.
4. افحص diff إن كان Git مهيأ، وإلا راجع الملفات المتغيرة مباشرة، بحثًا عن تغييرات غير مقصودة أو أسرار.
5. إذا تعذر تشغيل اختبار، اذكر السبب بوضوح ولا تدّعِ نجاحه.
6. لا تصلح اختبارًا بتعطيله أو إضعاف assertions إلا إذا كان ذلك هو المطلوب ومبررًا.

## 7. لا تدّعِ ما لم يحدث
- لا تقل إن الصفحة اختُبرت على الهاتف إذا لم تُختبر.
- لا تقل إن الأداء ممتاز دون قياس.
- لا تقل إن الدفع يعمل دون بيئة اختبار وإشعار تحقق.
- لا تقل إن المشكلة انتهت إذا لم تعِد إنتاجها أو تتحقق من إصلاحها قدر الإمكان.

## 8. شكل التسليم في نهاية كل مهمة
قدّم ملخصًا قصيرًا يتضمن:
- ما الذي تغير؟
- الملفات التي تغيرت.
- الاختبارات التي شُغّلت ونتائجها.
- الاختبارات التي لم تُشغّل وسبب ذلك.
- المخاطر أو القرارات المفتوحة.
- الخطوة التالية المقترحة.

## 9. إدارة القرارات
إذا تعارضت التعليمات أو كانت معلومة تجارية أساسية غير متوفرة:
- لا تخمّن.
- سجّل القرار بمعرف وحالة ومسؤول وأثر في OPEN_DECISIONS. استخدم ما هو مؤكد بالفعل، واستمر في العمل الذي لا يعتمد على المعلومة الغائبة.
- يمكن استخدام بيانات تجريبية موسومة بوضوح في بيئة التطوير فقط.

## 10. العقود والمرحلة الحالية

- اتبع MVP_SCOPE؛ أفكار خارج نطاق الإطلاق توضع في backlog، لا تدخل تلقائيًا أثناء التنفيذ.
- نموذج الواجهة المحلي الموجه إلى Gemini في CINEMATIC_FRONTEND_PLAN مسار مستقل داخل Phase 1: يبدأ بتكوين وحركة وبيانات معاينة موسومة، ولا يتوقف على قرارات الدفع والشحن. لا يشمل هذا الاستثناء نشرًا أو ربط تجارة أو ادعاء اكتمال Phase 2.
- لا تنسخ plane.md التاريخي إلى متطلبات حديثة ولا تعتبر أسعار الكتالوج وعبارات الصور معتمدة.
- أي تغيير في عقود السعر/الحجز/الدفع يحدث COMMERCE_CONTRACT واختبارات المرحلة المستهلكة له.
- لا تعلن PASS لاختبار لم يشغل، ولا تعتمد توثيق تعذر فحص حرج كبديل لنجاحه.
- لا تشغل وكلاء إضافيين أو توزع ملفات بالتوازي تلقائيًا؛ بروتوكول التسليم يستخدم عند طلب التعاون أو تفويضه.
