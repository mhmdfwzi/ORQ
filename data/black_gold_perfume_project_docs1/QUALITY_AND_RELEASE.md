# QUALITY AND RELEASE - دليل التحقق والتشغيل

هذه متطلبات قبول مستقبلية؛ **لم تشغل اختبارات تطبيق في مراجعة 2026-10-28 لعدم وجود كود**. تحفظ الأدلة الفعلية عند بدء التنفيذ، ولا تملأ النتائج بالتوقعات.

## 1. مستويات العيوب

- P0: كشف بيانات/أسرار، إجمالي أو تحصيل خاطئ، تكرار تحصيل، أو تلف بيانات/مخزون.
- P1: تعطل رحلة شراء أو إدارة طلب، كسر أساسي بالهاتف، أو تعذر الوصول إلى إجراء أساسي.
- P2: خلل غير مانع له حل بديل واضح.
- P3: تحسين بصري أو تحريري محدود.

لا إطلاق مع P0/P1 مفتوحة أو اختبار تجارة حرج غير منفذ. الملاحظات الأقل أثرًا تسجل بمسؤول وموعد. لا تستعمل درجة Lighthouse مرتفعة لتعويض فشل الشراء.

## 2. مصفوفة الاختبار

| الأولوية | السيناريو | الدليل المطلوب |
| --- | --- | --- |
| P0 | تغيير سعر/عملة/خصم في طلب المتصفح | الإجمالي من الخادم أو رفض المدخل؛ لا تعديل مالي غير مصرح |
| P0 | طلبان متزامنان لآخر قطعة | طلب واحد يحجز؛ الآخر يتلقى نفادًا؛ لا قيمة سالبة |

| P0 | webhook مكرر/معكوس الترتيب/بتوقيع غير صالح | رفض المزور؛ لا تكرار أثر أو تراجع حالة مؤكدة |
| P0 | اختلاف مبلغ/عملة أو فقد الإشعار | لا تأكيد خاطئ؛ مصالحة موثقة ومسار استثناء |
| P0 | انتهاء حجز مع تحصيل متأخر | تسجيل المال، وعدم تأكيد طلب بلا مخزون، ومعالجة استرداد/إعادة حجز |

| P1 | نفاد/تغير سعر بعد فتح السلة أو quote | تعارض مفهوم وإجمالي جديد يحتاج مراجعة العميل |
| P1 | انقطاع الشبكة، تحديث الصفحة، رجوع من المزود | سلة متسقة ولا طلب أو دفع مكرر |
| P1 | موظف دون صلاحية يغير سعرًا/طلبًا | رفض وسجل للعمليات الحساسة المصرح بها |

| P1 | نسخ واستعادة وإجراء rollback | دليل تجربة ووقت استعادة وقيود migrations |

اختبارات الوحدة لحساب الإجمالي وانتقال الحالات، وتكامل API للتفويض والمعاملات، وE2E لرحلة الشراء. اختبارات التزامن والحجز على نفس محرك قاعدة الإنتاج. اختبارات المزود الحقيقية في sandbox تكمل mocks؛ لا تستبدل بها.

الاختبارات المشروطة بطريقة دفع أو باقة غير داخلة في النطاق تسجل N/A مع مرجع D04 أو D07؛ لا تسجل PASS ولا NOT RUN لميزة مستبعدة بقرار. كل اختبار داخل النطاق يبقى مطلوبًا بحسب أولويته.

## 3. أدلة الواجهة والوصول

- مقاسات 320 و375 و390 و768 و1440px؛ RTL ونصوص عربية طويلة وأرقام/عملات واسم منتج طويل.
- فحص Chrome وSafari على هاتف فعلي إذا توفر؛ إن استعملت محاكاة فقط تسجل ذلك ولا تدّعي اختبار جهاز.
- لوحة مفاتيح، ترتيب focus، فتح/إغلاق dialogs والعودة لموضع التركيز، أخطاء حقول مرتبطة بها، وإعلان تغير السلة.
- تكبير النص 200% وتقليل الحركة وعدم الاعتماد على اللون أو hover وحده.
- لقطات للرئيسية والقائمة والمنتج والسلة وcheckout وحالات الخطأ في المقاسات الأساسية، مربوطة بإصدار وبيانات معروفة.
- قائمة [UI_ACCEPTANCE_CRITERIA.md](UI_ACCEPTANCE_CRITERIA.md) تخص الصفحات؛ هذه المصفوفة تخص النظام كاملًا.

## 4. الأداء قبل الإطلاق وبعده

**قبل الإطلاق:** قياسات lab على staging مطابق لإعداد الإنتاج، للهاتف المتوسط وشبكة محددة ثابتة. سجّل الجهاز/الأداة/الشبكة/الوقت/الإصدار، ونفذ 3 جولات لكل من الرئيسية والقائمة والمنتج وcheckout، واحتفظ بالنتائج والوسيط.

أهداف أولية للمراجعة:
- LCP ≤ 2.5s وCLS ≤ 0.1 تحت ظروف الاختبار المسجلة؛ أي إخفاق يحتاج إصلاحًا أو تخفيفًا موثقًا وإعادة قياس.
- فحص استجابة الإضافة للسلة والفلاتر والنماذج بتتبع تفاعلات؛ TBT مؤشر تشخيصي وليس قياس INP ميدانيًا.
- ميزانية مشروع مبدئية لصورة Hero المرسلة للهاتف ≤ 250KB، دون فيديو/3D في أول تحميل. تثبت أو تعدل بدليل الجودة والقياس عند اعتماد الصور في Phase 1؛ ليست معيارًا عالميًا.
- لا تحميل مؤثرات يسبق المنتج أو يعرقل CTA؛ محتوى Hero الأساسي ظاهر دون انتظار animation.

**بعد الإطلاق:** مراقبة LCP ≤ 2.5s وINP ≤ 200ms وCLS ≤ 0.1 عند المئين 75، مع فصل الهاتف والكمبيوتر. النتائج الميدانية تحتاج زيارات كافية؛ عدم توفرها يسجل «غير متاح»، ولا يحول إلى فشل قبل الإطلاق أو نجاح افتراضي.

هذه حدود [Core Web Vitals الرسمية](https://web.dev/articles/vitals)، مع تمييز واضح بين القياس الميداني والفحص المعملي.

## 5. قياس التجارة

يحدد D10 الأداة وسياسة الخصوصية. الأحداث المقترحة: view_item وadd_to_cart وbegin_checkout وorder_created، وpurchase بعد إثبات التحصيل، مع إشارة مستقلة لطلب COD غير المحصل.

- مصدر موثوق يمنع تكرار purchase بإعادة تحميل صفحة النجاح؛ لا يحسب الدفع المعلق كبيع محصل.
- لا ترسل اسمًا أو هاتفًا أو بريدًا أو عنوانًا أو رمز رابط الطلب لأدوات القياس.
- فصل تحويل الزيارة إلى طلب، وتحويل الطلب إلى تحصيل، وفشل الدفع، والإلغاء؛ نسبة COD تحتاج تتبع تحصيله.
- ابدأ بخط أساس فعلي، ثم راجع التسرب حسب الجهاز وطريقة الدفع. لا تثبت هدف نسبة تحويل دون بيانات.
- مراجعة أولية خلال أسبوعين ثم عند اكتمال عينة مفيدة؛ البيانات القليلة لا تبرر استنتاجات نهائية.

## 7. Runbook مختصر

1. حفظ معرف الإصدار وقائمة تغييرات البيانات، نسخة احتياطية متحققة، ونتائج staging؛ تحديد المسؤول ونافذة النشر.
2. نشر migrations متوافقة مع الإصدار السابق قدر الإمكان، ثم التطبيقين وتهيئة الأسرار وإعادة تشغيل workers حسب الحاجة.
3. smoke test: كتالوج وسلة وquote وطلب ودفع معتمد وحالة محمية ووصول الطلب للإدارة؛ تأكيد وصول logs والتنبيهات.
4. التفعيل بعد اعتماد صاحب المشروع. إذا احتاج الاختبار معاملة حية، تنفذ ضمن التفويض وبالمسار المسموح للمزود.
5. عند تكرار تحصيل/فساد مخزون/كشف بيانات: إيقاف checkout أو المسار المتأثر، حفظ الأدلة، وتسوية العمليات المعلقة مع المزود.
6. إعادة التطبيق إلى الإصدار السابق المتوافق عند الحاجة؛ لا تعكس migrations أو تستعد نسخة قاعدة قديمة تلقائيًا فوق طلبات جديدة. استرجاع البيانات يحتاج خطة تمنع فقد الطلبات وتراجع التسويات.
7. توثيق القرار والأثر ونتيجة الفحص بعد التراجع، ثم إعادة فتح البيع بعد تحقق الخلل.

## 8. قالب سجل التحقق

- التاريخ / المنفذ / الإصدار أو commit / البيئة:
- السيناريو ومعرف بيانات الاختبار دون معلومات شخصية:
- الأمر أو خطوات التفاعل الفعلية:
- المتوقع / الفعلي / PASS أو FAIL أو NOT RUN:
- رابط التقرير أو اللقطة أو سجل منقح:
- العيوب ومسؤول المعالجة:
- الاختبارات غير المنفذة وسببها، وأثرها على بوابة المرحلة:

عند بدء التنفيذ تحفظ التقارير في مجلد evidence/ أو مرفقات CI مرتبط بالإصدار. لا ترفع ملفات بيئة أو بيانات عملاء ضمن الأدلة.
