# DESIGN SYSTEM — Storefront UI Rules

## 1. الغرض
هذا الملف مرجع تنفيذ واجهات Next.js. لا تنشئ قيمًا متفرقة لكل صفحة. استخدم design tokens ومكونات مشتركة، وحدث هذا الملف عند اعتماد تغيير جوهري.

## 2. Tokens مبدئية
ضع القيم في CSS variables أو نظام tokens موحد. هذه قيم بداية وليست نهائية:
- `--color-obsidian: #111111`
- `--color-charcoal: #1C1A18`
- `--color-gold: #C4A265`
- `--color-ivory: #F2EBDD`
- `--color-smoked-brown: #292522`
- `--color-text-muted-dark: #B9B1A5`
- `--radius-sm: 6px`
- `--radius-md: 12px`
- `--radius-lg: 20px`
- `--content-max: 1280px`

اعتمد سلم مسافات ثابتًا مثل 4/8/12/16/24/32/48/64/96px، وتجنب القيم العشوائية المتكررة.

## 2.1 قيم بداية للنموذج

هذه اختيارات مشروع مقترحة تثبت بعد نموذج Phase 1، وليست مكونات منفذة:

- نص أساسي 16px على الأقل، وارتفاع سطر عربي مبدئي 1.7؛ لا تصغر نص السعر أو الحقول لإصلاح التخطيط.
- نقاط توقف أولية 640/768/1024/1280px، مع اختبار إعادة التدفق عند 320px.
- مساحة تفاعل أساسية مستهدفة 44×44px على الأقل، وفصل مناسب بين الأزرار.
- صورة البطاقة بنسبة موحدة يحددها النموذج، مع object-fit: contain للعبوة الكاملة؛ صور الحملات لها قص منفصل.
- حركات تفاعل قصيرة 150-250ms؛ كشف بصري بسيط 400-600ms؛ reduced-motion يلغي حركة المشهد غير الضرورية.
- عائلة عربية ولاتينية مع ترخيص استخدام واضح ومراجعة أسماء ORQ والأرقام؛ لا يعتمد خط نهائي قبل المقارنة على الشاشات.

## 3. Typography
- حدد عائلة عربية وعائلة لاتينية واضحة قبل تعميمها.
- استخدم أوزانًا محدودة ومتسقة.
- اجعل النص الأساسي مقروءًا على الهاتف؛ لا تقلل الحجم لتلائم التصميم.
- عناوين العرض قد تكون أنيقة ومميزة، لكن الوصف والسعر والحقول يجب أن تكون واضحة.
- اختبر الأرقام والعملات والعناوين الطويلة بالعربية والإنجليزية.
- لا تستخدم النصوص داخل صور ثابتة كبديل للنص الحقيقي.

## 4. Layout وResponsive
- ابدأ بتجربة الهاتف ثم وسّعها للشاشات الأكبر.
- استخدم نقاط توقف متسقة، لا media queries عشوائية لكل عنصر.
- لا يوجد overflow أفقي عند عرض 320px فما فوق إلا إذا كان جزءًا مقصودًا ومختبرًا.
- بطاقات المنتجات تحافظ على نسبة صور ثابتة مناسبة؛ استخدم `object-fit` بقرار واعٍ ولا تقص العبوة.
- لا تجعل المحتوى الأساسي يعتمد على hover؛ اللمس لا يملك hover مماثلًا.
- اختبر RTL فعليًا، بما في ذلك ترتيب الأيقونات، الأسهم، breadcrumb، النماذج، والأرقام.

## 5. المكونات الأساسية
أنشئ مكونات قابلة لإعادة الاستخدام عند الحاجة:
- Header / Mobile navigation
- Footer
- Button بأحجام وحالات واضحة
- ProductCard
- ProductGallery
- Price / Compare-at-price عند وجود سعر مقارنة صحيح
- QuantitySelector
- AddToCartButton وحالاته
- FilterDrawer للموبايل وFilters للشاشات الواسعة
- Search
- Breadcrumb
- FormField ورسائل الخطأ
- EmptyState / LoadingState / ErrorState
- CartSummary
- Toast أو feedback accessible
- Dialog/Drawer قابل للاستخدام بلوحة المفاتيح

لا تبالغ في تجزئة المكونات الصغيرة جدًا. أعد الاستخدام حيث يوجد سلوك أو شكل متكرر فعلًا.

## 6. حالات الواجهة
لكل تفاعل مناسب، صمم الحالات التالية:
- Default
- Hover (للأجهزة التي تدعمه)
- Focus-visible
- Active/Pressed
- Disabled
- Loading
- Error
- Success
- Empty/Unavailable عند اللزوم

لا تستخدم لونًا فقط لتوضيح الخطأ؛ أضف نصًا أو علامة مناسبة.

## 7. قواعد Product Card
- صورة حقيقية ونسبة ثابتة.
- اسم واضح، وحجم/تركيز فقط إذا كانت بياناته متاحة.
- سعر صحيح ومرئي.
- إظهار الخصم فقط إذا كان السعر الأصلي والخصم حقيقيين.
- حالات نفاد المخزون واضحة.
- لا تضع عدة أزرار متنافسة في مساحة صغيرة.
- النقر على الصورة أو الاسم يفتح صفحة المنتج، مع دعم عناصر التحكم بشكل مستقل.

## 8. الوصول
- تباين مناسب للنصوص والأزرار.
- تنقل بلوحة المفاتيح ومؤشر focus واضح.
- labels مرتبطة بالحقول.
- صور لها alt مناسب؛ الصور الزخرفية alt فارغ.
- أزرار بأسماء مفهومة لقارئات الشاشة.
- دعم `prefers-reduced-motion`.
- لا تستخدم عناصر غير دلالية بدل button/link دون سبب.

## 9. الأداء
- استخدم Next.js Image أو استراتيجية صور مناسبة.
- لا تحمّل مكتبة 3D في MVP؛ راجع MVP_SCOPE. أي مكتبة حركة جديدة تحتاج سببًا وقياسًا.
- اجعل المكونات التفاعلية client-side فقط عندما تحتاج state أو browser APIs.
- تجنب تحميل فيديو ضخم أو صور أصلية غير محسنة في أول شاشة.
- امنع layout shift بتحديد الأبعاد أو aspect ratio.
- لا تضف مكتبات قبل التأكد من الحاجة وحجمها.

## 10. Definition of Done للمكون
- يتبع tokens.
- يعمل على الهاتف والكمبيوتر.
- يملك حالات التفاعل اللازمة.
- لا يسبب أخطاء console أو accessibility واضحة.
- لا يكرر منطقًا موجودًا بلا داعٍ.
- أضيفت اختبارات مناسبة إذا كان السلوك غير بسيط.

## 11. سلوك المكونات في الرحلة التجارية

- Dialog/Drawer: إدارة focus وحبسه عند كونه modal، دعم Escape، وإعادة focus إلى زر الفتح؛ قفل التمرير لا يمتد لما بعد الإغلاق.
- الفلاتر: القيم في URL، زر مسح واضح، احتفاظ بالفرز، وعدد نتائج من الخادم. لا تعرض فلترًا لبيانات غير مكتملة.
- Cart/Checkout: تغيير السعر أو نفاد النسخة حالة مستقلة برسالة وإجراء واضح، لا toast يختفي قبل أن يقرأه العميل.
- AddToCart: اسم النسخة والكمية في feedback قابل للإعلان لقارئ الشاشة؛ زر loading لا يمنع معالجة retry الصحيح في API.
- تأكيد الطلب: pending payment وpaid وCOD unpaid حالات مختلفة، ولا يعرض نجاح التحصيل لمجرد رجوع المتصفح.
- لا تفقد بيانات العنوان عند validation؛ لا تخزن بيانات دفع حساسة في حالة الواجهة.
- أي زر شراء ثابت على الهاتف يراعي safe area ولوحة المفاتيح ولا يغطي المحتوى أو أخطاء الحقول.
- تفاصيل ميزانية الصور والقياس في QUALITY_AND_RELEASE؛ لا تدّعِ جودة الأداء من شكل النموذج.
