# IMPLEMENTATION PHASES - خطة التنفيذ

آخر تحديث: 2026-10-28. **المرحلة الحالية Phase 0 قيد التجهيز؛ لم تنفذ أي مرحلة برمجية.** انتهى جرد الوثائق والأصول في هذه المراجعة، بينما القرارات التجارية والبيانات لم تعتمد بعد.

أضيف مسار واجهة مستقل موجه إلى Gemini في [CINEMATIC_FRONTEND_PLAN.md](CINEMATIC_FRONTEND_PLAN.md)، مع [برومبت تسليم جاهز](GEMINI_FRONTEND_PROMPT.md). مهام CINE-00 إلى CINE-03 هي نموذج Phase 1 محلي يمكن البدء به بالتوازي مع قرارات Phase 0؛ لا تشمل ربط تجارة أو اجتياز تأسيس التطبيقين. الحالة ما زالت «لم يبدأ التنفيذ» حتى يقدم دليل فعلي.

## 1. طريقة العمل

- كل مهمة لها مرحلة ومرجع ومتطلبات سابقة ومخرجات ودليل قبول.
- لا يبدأ مسار يعتمد على بوابة غير مستوفاة. الأعمال المستقلة مثل تجهيز المحتوى أو جرد الصور يمكن أن تستمر.
- لا يشترط إنهاء كل الخلفية قبل تجربة الواجهة؛ نبني رحلة منتج واحد كاملة مبكرًا، ثم نعممها.
- المراحل ليست مددًا زمنية. بعد Phase 0 يسجل المنفذ تقدير أيام العمل والتبعيات الخارجية لكل مرحلة؛ مدة انتظار المحتوى/الحسابات/الاعتماد تسجل منفصلة.
- صاحب المشروع يحسم التجارة والاتجاه؛ المنفذ مسؤول عن العقد والكود والاختبارات؛ التشغيل مسؤول عن تنفيذ الطلبات. يمكن أن يقوم شخص واحد بأكثر من دور.
- PASS يعني أدلة مكتملة ونجاح الفحوص المطلوبة. توثيق سبب تعذر اختبار لا يحوله إلى نجاح.

## Phase 0 - Discovery, Scope & Product Readiness

**المسؤول:** صاحب المشروع مع المنفذ ومسؤول المنتجات.

العمل:
- جرد الموجود فعليًا وتسجيل مصدر البيانات: تم في مراجعة الخطة.
- تثبيت MVP وحسم D07 بشأن الباقة قبل إقفال نموذج البيانات.
- حسم D02 وD05 وD06 وقواعد D08 الأساسية؛ تحديد مسار D04 واحتياجات حساب المزود.
- تجهيز سجل SKU واحد على الأقل وفق PRODUCT_DATA؛ بقية المنتجات لها قائمة نواقص.
- تحديد أصول الهوية D01/D09، وجهة staging والميزانية المبدئية D11، ومن يدير الطلبات D12.
- رسم نموذج أولي للمنتج/النسخة/المخزون/الطلب/الدفع؛ إضافة مكونات الباقة فقط إذا اعتمدت.

**المخرجات:** سجل قرارات محدث، MVP محدد، سجل SKU، خريطة أصول، تدفق شراء، ونموذج بيانات مبدئي.

**البوابة:** D02/D05/D06/D07 وقواعد الشحن اللازمة مؤكدة؛ طريقة الدفع المطلوبة محددة؛ سجل SKU واحد مكتمل؛ لكل قرار متبق مسؤول وموعد حسم. لا يكفي مجرد تسجيل مجهول يؤثر على الإجمالي.

## Phase 1 - Visual Proof

**المسؤول:** Gemini لتنفيذ نموذج الواجهة حسب التكليف الحالي؛ صاحب المشروع يعتمد الاتجاه.

**مسار البدء:** CINE-00 إلى CINE-03 ثم GATE-VISUAL وفق CINEMATIC_FRONTEND_PLAN. لا تمنع أسعار أو شحن أو بوابة دفع غير محسومة نموذجًا محليًا موسومًا. إن غاب التطبيق، يسمح بإنشاء الحد الأدنى في frontend/ لتشغيل المعاينة؛ لا يشمل ذلك Laravel أو إعداد نشر أو ربطًا تجاريًا. بعد الاعتماد تنفذ CINE-04 إلى CINE-06، ويبقى قبول التجارة منفصلًا.

- نموذج الرئيسية وصفحة المنتج على 375 و390 و1440px، مع فحص ضيق 320px.
- استخدام منتجات وصور مطابقة أو placeholders موسومة في النموذج فقط.
- توضيح السلة وإتمام الطلب وحالات التوفر والخطأ؛ لا نراجع Hero بمعزل عن الشراء.
- Hero ثابت صالح للاستخدام أولًا؛ الحركة طبقة تحسين خفيفة. تحديد typography وtokens والتباين وRTL.
- ربط كل صورة بدورها، وتحديد الأصول التي تحتاج بديلًا قبل التنفيذ النهائي.

**المخرجات:** مرجع مرئي محفوظ ومؤرخ، نسخ الهاتف/الكمبيوتر، وسجل اعتماد D01/D09 اللازم للصور النهائية.

**البوابة:** صاحب المشروع راجع التكوين، والمنتج والسعر وCTA واضحون، والنموذج قابل للتنفيذ دون 3D أو حظر التمرير. لا تعميم قبل اعتماد الاتجاه.

## Phase 2 - Foundations, API & Staging

**المسؤول:** المنفذ.

- فحص PHP/Composer/Node ومديري الحزم وقاعدة البيانات والاستضافة، ثم اختيار إصدارات مدعومة متوافقة وتثبيتها.
- إنشاء Git وbackend/ وfrontend/ عند غيابها، مع الحفاظ على أساس frontend/ إن أنشئ للنموذج؛ لا إعادة تأسيس أو نشر أو ربط remote تلقائيًا.
- إعداد .env.example بلا أسرار، أوامر التشغيل، migrations، فحوص الكود والأنواع والاختبارات والبناء، وCI.
- تحويل COMMERCE_CONTRACT إلى OpenAPI مطابق للنسخ الفعلية؛ عينات استجابات ومخطط أخطاء.
- حسم المتصفح ← API مباشرة أو عبر Next.js قبل تطبيق الجلسات؛ توثيق cookies وCSRF وCORS والتفويض.
- إعداد staging بمعزل عن الإنتاج وفحص صور/قاعدة بيانات وصحة التطبيق؛ لا بيانات عملاء حقيقية.
- بناء tokens وHeader وButton وFormField وProductCard بالحد اللازم للرحلة الأولى.

**المخرجات:** تطبيقان يعملان محليًا، إعداد تحقق قابل للتكرار، OpenAPI، ونسخة staging أولية محمية من الفهرسة العامة.

**البوابة:** تشغيل التطبيقين واتصال API يعملان؛ فحوص التأسيس ناجحة؛ نموذج الجلسة وحماية البيانات مثبتان، وتعليمات الإعداد مجربة. غياب استضافة معتمدة لا يمنع العمل المحلي، لكنه يبقي جزء staging من البوابة مفتوحًا.

## Phase 3 - One Product, Complete Purchase

**المسؤول:** المنفذ؛ مسؤول المنتجات يوفر سجل SKU؛ التشغيل يجرب الطلب.

- تنفيذ منتج/نسخة وصور وسعر ومخزون، وإدارة بسيطة محمية لتعديلها.
- ربط PDP والسلة وcheckout بعقد Laravel الفعلي، وحفظ السلة وفق D05.
- quote من الخادم، تحقق شحن، إنشاء طلب بمعاملات وحجز مخزون وIdempotency-Key.
- دمج مسار الدفع المعتمد مبكرًا: sandbox للمزود الإلكتروني، أو حالة COD إذا اعتمدت وحدها. محاكاة المزود تسمح بتقدم التطوير لكنها لا تحقق بوابة تكامل الدفع الإلكتروني.
- تأكيد محمي، وظهور الطلب للإدارة، وإلغاء/تحرير حجز وتحديث الحالة.
- إذا كانت الباقة شرط إطلاق، تكون جزءًا من هذه الرحلة المبكرة، لا تؤجل مخاطرة نموذجها إلى آخر المشروع.

**دليل القبول:** رحلة فعلية عبر الواجهة، واختبارات تغيير السعر وآخر قطعة والتزامن والتكرار والوصول لطلب آخر. عند الدفع الإلكتروني: تحقق خادمي sandbox ناجح وفاشل ومكرر.

**البوابة:** طلب واحد صحيح من هاتف إلى الإدارة؛ لا أسعار موثوقة من المتصفح؛ لا خصم مزدوج أو مخزون سالب؛ لا تأكيد دفع من redirect وحده. المنتج النموذجي والاختبارات متوافقون مع قواعد التجارة المعتمدة.

## Phase 4 - Storefront & Catalog Expansion

**المسؤول:** المنفذ مع مسؤول المحتوى.

- تعميم المكونات المعتمدة على الرئيسية والقائمة والمنتج والبحث والفلاتر والسلة والثقة.
- استيراد المنتجات التي اجتازت PRODUCT_DATA فقط؛ تنظيف الأسماء والروابط وربط الصور.
- استكمال إدارة الكتالوج والمخزون والطلبات والصلاحيات والتدقيق.
- حالات الخطأ والتحميل والفراغ ونفاد المخزون وتغير الأسعار على كل شاشة.
- metadata وcanonical وsitemap/robots؛ لا بيانات خاصة ضمن الفهرسة.
- فحص بصري تدريجي على المقاسات المستهدفة بدل تأجيله لنهاية المشروع.

**البوابة:** النطاق المتفق عليه قابل للاستخدام بلا روابط وهمية؛ كل SKU منشور معتمد؛ الصفحات تجتاز UI_ACCEPTANCE_CRITERIA؛ الإدارة لا تحتاج تعديل قاعدة البيانات يدويًا.

## Phase 5 - Integrations & Daily Operations

**المسؤول:** المنفذ مع التشغيل.

- استكمال الدفع: إشعارات موقعة، تكرار وترتيب وتأخر الأحداث، تطابق المبلغ/العملة، مصالحة عند فقد الإشعار، واسترداد وفق D04.
- قواعد الشحن المعتمدة؛ تسليم يدوي موثق أو تكامل شركة الشحن بحسب D08، دون افتراض API ضروري.
- إشعار تأكيد وقنوات معتمدة؛ retries دون إعادة إنشاء الطلب أو تحصيل جديد.
- worker وscheduler للمصالحة وانتهاء الحجوزات؛ متابعة المهام الفاشلة.
- تجربة يوم عمل: طلب، تعبئة، شحن، إلغاء، تحصيل متأخر، واسترداد. COD لا يصبح paid قبل إثبات التحصيل.
- تحديد RPO/RTO والنسخ الاحتياطي والتنبيهات ومسؤول الاستجابة في خطة التشغيل.

**البوابة:** السيناريوهات المختارة مجربة في staging؛ المزودون والعمليات جاهزون؛ حالات الاستثناء لها مسار معالجة ومسؤول. لا وصف لتكامل غير مختبر بأنه جاهز.

## Phase 6 - Release Validation

**المسؤول:** المنفذ؛ التشغيل يراجع إجراءات العمل؛ صاحب المشروع يعتمد المحتوى.

- تشغيل مصفوفة QUALITY_AND_RELEASE واختبارات التجارة على نفس محرك قاعدة الإنتاج.
- مراجعة الهاتف وRTL ولوحة المفاتيح وتقليل الحركة وSEO والأمان وخصوصية البيانات.
- قياس أداء staging بأسلوب قابل للتكرار؛ إصلاح الصور والحركة ضمن الميزانية.
- تجربة نسخ واستعادة فعلية، ومراجعة خطة نشر وrollback متوافقين مع migrations.
- اختبار أحداث القياس دون بيانات شخصية، وتحضير بيانات الإنتاج المعتمدة فقط.

**البوابة:** كل اختبارات P0 ناجحة؛ لا عيوب P0/P1 مفتوحة؛ أدلة المراجعة محفوظة. غياب بيانات CWV الميدانية قبل الزوار يسجل «غير متاح» ولا يدّعى نجاحه. ملاحظات بسيطة متبقية لها مسؤول وموعد.

## Phase 7 - Launch & Observe

**المسؤول:** المنفذ مع التشغيل؛ صاحب المشروع يحدد موعد الإطلاق ويعتمده.

- قبل التفعيل: حسابات حية ومفاتيح آمنة ودومين وHTTPS ونسخ وworker وscheduler وتنبيهات.
- نشر تدريجي وفق runbook؛ smoke test للعرض والسلة والشحن والدفع المعتمد وحالة الطلب.
- تجربة معاملة حية محدودة فقط ضمن تفويض الإطلاق وقواعد المزود، وتوثيق نتيجة التسوية/الاسترداد إذا كانت مطلوبة.
- مراقبة الدفع والمخزون وأخطاء checkout وطوابير العمل بعد الإطلاق؛ عند خلل مالي/خصوصية يوقف checkout ويطبق إجراء التراجع.
- متابعة مؤشرات الأداء والتحويل خلال أول أسبوعين وعند توفر عينة كافية؛ تحسينات لاحقة مرتبة حسب البيانات.

**البوابة:** النسخة الحية تعمل، المراقبة تصل للمسؤول، ويمكن تنفيذ الطلبات والاسترجاع. تشغيل staging وحده لا يحقق إطلاقًا.
