# PROJECT BRAIN - ORQ Men's Fragrance

آخر مراجعة: 2026-10-28.

## 1. الهدف والثوابت

متجر عطور **رجالية فقط**، بفخامة سوداء وذهبية وحركة سينمائية محسوبة، مع شراء سهل من الهاتف. Laravel هو Backend مستقل، وNext.js هو Frontend مستقل؛ لا تغير هذا الاختيار ضمن مهمة تصميم أو تحسين وثائق.

الأولويات: صحة المنتج والسعر والمخزون والطلب، ثم سهولة الشراء، وجودة الهوية، والأداء، وقابلية الصيانة والبحث.

## 2. الحالة الفعلية

- مرحلة تخطيط؛ لا يوجد تطبيق أو مستودع Git في المجلد وقت المراجعة.
- يوجد كتالوج يسرد 12 اسم عطر مع أوصاف وأسعار **مقترحة** لـ100 مل.
- توجد 7 صور تحمل ORQ وعبارة OWN YOUR PRESENCE، بينها عروض باقات ومقاسات مختلفة. وجود الصورة لا يثبت مطابقتها لعبوة البيع أو حقوق استخدامها.
- ORQ اسم العمل المستند إلى الأصول؛ تأكيد الشعار والكتابة النهائية ضمن D01.
- Black Gold اتجاه فني داخلي وليس اسم منتج أو علامة جديدة.
- MySQL قاعدة البيانات المستهدفة في الخطة؛ يراجع توافق نسختها والاستضافة قبل التثبيت.
- العربية وRTL أساس النطاق المقترح؛ الإنجليزية مؤجلة ما لم تعتمد ضمن D02.

## 4. نطاق الإصدار الأول

الرئيسية، قائمة المنتجات، تفاصيل المنتج، بحث وفرز وفلاتر بسيطة ببيانات حقيقية، السلة، إتمام الطلب، حالة الطلب المحمية، صفحات الثقة، ولوحة إدارة أساسية للمنتجات والمخزون والطلبات. التفاصيل والتوسعات في [MVP_SCOPE.md](MVP_SCOPE.md).

الشراء كضيف، بلد واحد، عملة واحدة، ومستودع واحد اقتراحات لتقليل نطاق البداية؛ تحتاج حسم D02/D05/D06، وليست إعدادات بيع معتمدة.

## 5. المعمارية المقترحة

- تطبيقان في مجلد عمل واحد: backend/ وfrontend/، لتسهيل تتبع العقود والتغييرات؛ هذا هيكل مقترح لم ينشأ بعد.
- Laravel المالك الوحيد لقواعد التجارة وقاعدة البيانات؛ Next.js يعرض البيانات ويقدم التفاعل عبر API. لا وصول مباشر لقاعدة البيانات من الواجهة.
- فصل بيانات الكتالوج العامة عن بيانات السلة والعميل والطلب. لا توضع الأخيرة في cache عام.
- API موثق قبل الربط، مع مصادقة وتفويض في Laravel مهما كان مصدر الطلب.
- دفع وشحن من خلال تكاملات محدودة بالمزود المعتمد، دون بناء نظام لكل مزود محتمل.
- مهام خلفية للإشعارات والمصالحة، ووسائط قابلة للنسخ الاحتياطي. Redis وCDN ومحرك بحث خارجي ليست شروطًا تلقائية للبداية.
- تثبت الإصدارات المدعومة المتوافقة عند التأسيس بعد فحص البيئة والوثائق الرسمية، وتسجل في ملفات الحزم والقفل؛ لا نفترض رقم إصدار من الخطة.

## 6. قواعد البيانات والادعاءات

لا تعتمد سعرًا أو مخزونًا أو حجمًا أو تركيزًا من صورة إعلانية. لا تحول أسماء العطور المرجعية في عمود Original Names إلى علامات المنتجات المباعة. أوصاف النفحات وادعاءات الثبات تحتاج مراجعة المنتج قبل النشر. تفاصيل الجاهزية في [PRODUCT_DATA.md](PRODUCT_DATA.md).

## 7. تعريف النجاح

- رحلة صحيحة من اكتشاف SKU متاح إلى طلب يمكن للإدارة تنفيذه وتتبع دفعه وشحنه.
- لا زيادة بيع لآخر قطعة تحت التزامن، ولا مضاعفة طلب أو تحصيل أو خصم مخزون عند إعادة المحاولة.
- لا تسريب لبيانات عميل عبر رابط حالة طلب أو cache أو logs.
- واجهة متسقة ومقروءة على الهاتف وRTL مع دليل مراجعة بصري فعلي.
- اختبارات التجارة الحرجة ناجحة، ونشر قابل للمراقبة والاسترجاع.
- قياس التحويل والأداء بعد الإطلاق وفق خطة القياس؛ لا وعد بنسبة مبيعات أو نتيجة أداء قبل القياس.
